# Готовность интерфейса к локализации

Статус аудита: **выполнен 14 августа 2026 года**.

## Граница локализации

- Пользовательский текст frontend хранится в feature-owned `i18n/*-translations.ts` или в общем `shared/i18n/common-translations.ts`.
- Backend возвращает стабильный `code` и централизованное английское диагностическое сообщение. Frontend выбирает локализованный текст по `code`; текст backend не используется как UI-fallback.
- Технические идентификаторы, значения протокола, логи и сообщения исключений разработчика не являются пользовательским текстом и не переводятся.

## Что проверено

- JSX-текст и строковые выражения;
- `label`, `title`, `message`, `description`, `placeholder`, tooltip и ARIA-подписи;
- сообщения об ошибках и fallback-ветки;
- форматирование дат и времени;
- сортировка пользовательских названий;
- совпадающие значения переводов во всех поддерживаемых языках (`en`, `ru`, `uk`, `pl`).

## Автоматические проверки

```bash
npm run check:i18n
npm run audit:i18n-duplicates
```

`check:i18n` обязателен и входит в полный `npm run check`: он проверяет одинаковый набор ключей локалей и запрещает новый hardcoded UI-текст, включая locale-sensitive форматирование без выбранной локали.

`audit:i18n-duplicates` — отчёт для ручного semantic review. Совпадение строк само по себе не всегда означает дубликат: одинаковое слово в заголовке, статусе и действии может требовать разных форм в другом языке. Объединять нужно только ключи с одной и той же семантикой.

## Правило для новых API-ошибок

1. Backend добавляет стабильный error code.
2. Frontend сопоставляет code с i18n-ключом.
3. Для неизвестного code используется локализованное общее сообщение.
4. Поле `error` ответа не показывается пользователю напрямую.
